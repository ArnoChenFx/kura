## 需求（用户在真实使用中提的两条）

### 需求 A：一个仓库里有多个技能时，支持多选安装

现在的行为（`internal/store/add.go` 的 `discoverForAdd` + `internal/ui/install.go`
的 `DiscoverInstallCandidatesAsync` / `viewInstallCandidates`）：

- 仓库里恰好一个候选 → 自动装上；
- 多个候选 → 列出候选，**点一个**填进「子目录」输入框，再点「安装」装**那一个**。

用户要的是：**多选，一次装好几个**。从 mattpocock/skills 这种仓库（38 个技能）装技能
时，一个个装太笨。

要求：

1. **store 层新增批量安装 API**（放 `internal/store/add.go`，名字你定，建议
   `AddMany`）。要点：
   - **对同一个仓库只 clone 一次**：用户选了同一个 repo 里的 N 个技能，只做一次
     `cloneUpstream`，用 `upstream.Checkout([]string{...})` 一次检出 N 个目录
     （`Checkout` 已经接受多个 subPath，见 `internal/store/upstream.go`——那个文件
     不要改，直接调）。不要 N 次 clone、不要 N 次 checkout。
   - 逐项返回结果（参考 `UpdateMany` 的 `[]UpdateResult` 形状：`Name` + `Result` +
     `Err`），**单项失败不影响其他项**（比如第 3 个目标目录已存在同名技能，前 2 个
     和后面几个照装）。错误信息里要能看出是哪一个技能失败了。
   - 复用既有的 `installDir`，不要把「复制 + 写元数据」再实现一遍。
   - `Add`（单个）的现有行为、错误文案、`CandidatesError` 语义都**不许变**——CLI 与
     既有测试都依赖它。批量 API 是新增，不是替换。

2. **UI 候选列表改成可多选**（`internal/ui/install.go`）：
   - 每个候选一行一个**复选框**（MyGo 有 `myui.Checkbox(c, *bool, label)`），默认
     **全不选**；行尾/顶部给一个「全选」/「全不选」的切换（用你判断合适的控件，
     简单的话一个 `myui.Button` 就够）。
   - 主按钮文案随选中数变化：0 个时禁用并写「安装选中的技能」，N>0 时写
     「安装选中的 N 个」。点击后调用批量 API，**一次装完选中的全部**。
   - 装的过程中 `busy` 语义不变（显示 spinner、按钮禁用）；装完的结果报告要能让
     用户看出「装成了几个、哪几个失败、为什么」——状态行（`a.status` /
     `a.statusErr`）给一句话摘要，失败明细留在弹窗里（`install.err` 显示失败项）。
     全部成功时照旧清空表单并选中最后一个装上的技能。
   - 「唯一候选自动装」与「手动填了子目录就装那一个」两条既有路径**行为不许变**。
   - `installState` 里现在的 `cands []string` 可以扩成带选中状态的类型；改的时候
     把 `internal/ui/install_discover_test.go`、`internal/ui/install_test.go`、
     `internal/ui/design_shots_test.go` 里用到 `cands` 的地方一起更新
     （design_shots_test.go 里 `installState{...}` 的构造要能编译）。

### 需求 B：装进来的技能，默认名字取 SKILL.md 里的技能名

现在的行为（`internal/store/add.go` 的 `installDir`）：`nameOverride` 为空时取**来源
目录名**（`filepath.Base(srcDir)`）。于是 `skills/engineering/tdd/` 装进来叫 `tdd`——
恰好碰对是因为这些仓库的目录名和技能名一致，但这是巧合。

用户要的是：默认名取 **SKILL.md frontmatter 的 `name:` 字段**（就是技能自己的名字）。

要求：

1. **只改默认值的来源，优先级不变**：显式 `AddOptions.Name`（UI 的「安装名称」输入框
   / CLI 的 `--name`）永远第一；没给时才用 frontmatter 的 `name:`；frontmatter 也没有
   （或不可用）时**退回目录名**——一个字都不能变。
2. 读 frontmatter 要复用 `internal/store/skillmd.go` 的现有读法（`readDescription`
   的扫描逻辑就在那里，`name:` 与 `description:` 同属 frontmatter，别另写一套 YAML
   解析、别引依赖）。`name` 可能是带引号的单行值，按 `unquote` 的既有规则处理。
3. **名字必须能当目录名用**，否则退回目录名（不要报错——用户没做错什么，只是仓库里
   的 frontmatter 不讲究）。判据至少包括：非空、不是 `.` / `..`、不含 `/` 或 `\`、
   不含 `..`、不含 Windows 非法字符 `<>:"|?*`、不以空格或点结尾。可以复用
   `internal/store/cli_support.go` 里已有的名字校验（看好它的语义再决定要不要直接用，
   它现在用于「防目录穿越」，可能比这里需要的更严——**如果直接复用会误拒合法技能名，
   就写一个更适合的判据并在注释里说明为什么不复用**）。
4. 名字被改成「技能名」之后，重名检测照旧（`installDir` 里的 `fileExists(dst)`），
   报错文案保持现有的「根目录已存在同名技能 <name>」。
5. 元数据里的 `ID` / `DisplayName` 跟着装进来的名字走（现在就是这样，别改坏）。
