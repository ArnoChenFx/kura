## 缺陷 1：发现还在跑的时候改「仓库」，回来时会自动装到新仓库上

复现（我用一次性探针在 `internal/ui` 里跑的，跑完删了）：

1. 仓库输入框填 `owner/inflight-a`（该仓库里只有 `skills/solo-a` 一个技能）。
2. 点「安装」→ 进入发现（后台 clone + 扫描）。
3. 发现还没回来时，用户把仓库改成 `owner/inflight-b`（B 里是 `skills/gamma`、
   `skills/delta`）。
4. 发现回来：`DiscoverInstallCandidatesAsync` 的完成回调走 `len(cands) == 1` 分支，
   做的是 `s.subPath = cands[0]`（**A 的路径**）然后 `startInstall(a, s.installOptions())`
   ——`installOptions()` 读的是**当前表单**（B）。

实测两种结局：

- B 里恰好也有同名目录（我让 B 也有 `skills/solo-a`，内容写的是「这是仓库 B 的内容」）：
  弹窗自己关掉、状态行「已安装 solo-a」——**用户没点第二次安装**，装的是 B 的内容。
- B 里没有这个目录：报 `store: 仓库内不存在目录 skills/solo-a`，用户一头雾水
  （他只是在改仓库名，没打算装任何东西）。

要求：

- 发现的**完成回调**必须先判断「这次发现用的 repo/ref 与当前表单是否还一致」：
  不一致就**丢弃这次结果**（不填候选、不写 subPath、不自动安装、不报错），
  等用户下一次动作按新表单重新发现。判据可以复用你已有的
  `candsLive()`/比较逻辑，但注意单候选这条路径上 `cands` 是空的，
  `candsLive()` 直接返回 false，所以要按「发现时的 repo/ref」显式比较，
  别用「表单现在有没有候选」来判断。
- 多候选分支也照这个判据再确认一遍（我探到的是：多候选时 `candsLive()` 为假、
  列表不显示、有「仓库或分支已改」提示——这条行为我看着是对的，但请你写进测试钉死）。
- **绝不可以在用户在途改仓库后发起任何安装**。

回归测试（要能在修复前失败，照旧先临时退回修复跑一次、把原始输出贴出来）：

- 用例：挂起 spawn（不跑后台任务）→ 用 A 点安装（只发起发现）→ 把表单改成 B →
  放行发现 → 断言：① 根目录里**没有**任何新技能；② 没有发起后续安装
  （比如断言 `s.subPath` 没被写成 A 的路径 / 或 spawn 调用次数没增加）；
  ③ 再点一次安装按 B 重新发现。
- 名字自拟，风格照 `install_discover_test.go` 里已有的（本地 bare + `insteadOf`，
  不联网）。
